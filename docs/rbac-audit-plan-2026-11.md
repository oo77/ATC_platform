Дата: 2026-11-08. Основано на разборе кода: `server/api` (398 эндпоинтов), `server/middleware/auth.ts`, `server/utils/permissions.ts`, `app/types/permissions.ts`, `server/utils/activityLogger.ts`, `activity_logs`.

## 0. Сначала: критические дыры (исправить до всего остального)

Сервер пускает запрос **без токена** на любой путь, которого нет в `ROLE_PROTECTED_ROUTES` (`server/middleware/auth.ts`). Сам эндпоинт должен проверять права, но многие этого не делают. Проверено чтением кода:

| Эндпоинт | Что может сделать кто угодно |
|---|---|

| `POST /api/environment/restart`, `migrate`, `test-connection`, `GET check-db`, `current` | перезапустить сервер, запустить миграции, увидеть настройки БД **без входа** |
| `GET /api/maintain/fix-certificate-paths` | массово изменить пути сертификатов без входа |

| `POST/PUT /api/courses`, `/api/courses/[id]/disciplines*` | создать или изменить учебную программу без входа |

## 1. Как устроено сейчас

**Три параллельных и рассинхронизированных механизма доступа:**

1. `ROLE_PROTECTED_ROUTES` в серверном middleware: проверка **по ролям** и по префиксу URL. Это единственное, что работает глобально.
2. `requirePermission(...)` в эндпоинтах: используется в 58 из 398 файлов. Права берутся из захардкоженного `ROLE_PERMISSIONS`.
3. `API_PERMISSIONS` + `checkApiAccess()` в `server/utils/permissions.ts`: таблица описана, но **нигде не вызывается** (мёртвый код).

Плюс ещё около 41 файла, где сравнивается `user.role === 'ADMIN'` напрямую, и около 9 файлов на клиенте (например, `app/pages/users/index.vue` с вкладками по ролям).

**Другие проблемы:**
- Роль хранится как `ENUM('ADMIN','MANAGER','TEACHER','STUDENT')` в `users.role` и вшита в JWT. Новую роль добавить нельзя без миграции и правки кода.
- Права в двух копиях (`app/types/permissions.ts` и `server/types/permissions.ts`), они уже расходятся.
- Область данных («свои группы» или «все группы») вычисляется **по роли** (`canAccessGroup`: ADMIN/MANAGER видят всё, TEACHER свои). Для кастомной роли это не сработает.
- Права из `Permission` грубые: `LIBRARY_MANAGE` покрывает загрузку, удаление, выдачу доступа и аналитику сразу; `TEST_BANKS_MANAGE` объединяет создание, правку, удаление и импорт.
- Целых модулей нет в каталоге прав: аудитории, AI-чат, AI-настройки, конструктор отчётов, заявки на обучение, Telegram-бот, поддержка, планировщик курсов, учёт отметок (запросы на отметку), переносы и копирование расписания, шаблоны расписания, документы групп (протоколы, ведомости), публичные дашборды (повешено на `DASHBOARD_STATS`).

**Журнал действий (`activity_logs`):**
- `logActivity` вызывается в 120 местах, но пишет только «кто, действие, тип сущности, id, имя». Изменения (было → стало) не пишутся почти нигде.
- Колонки `action_type` и `entity_type` это ENUM. Значения из кода, которых нет в ENUM (например, `TEST` удалён миграцией 033, `LIBRARY_BOOK` терялся до 053), молча не записываются: ошибка проглатывается в `try/catch`.
- Нет записи отказов в доступе (403), неудачных входов, изменений ролей и прав.
- Нет связи с запросом (request id), нет результата (успех или ошибка), нет «от чьего имени».
- Нет ни неизменяемости, ни политики хранения: `deleteOldActivityLogs` удаляет физически.
- Модули без логов вообще: аттестация (0 из 24), организации (0 из 13), тесты (0 из 13), AI-настройки, публичные дашборды, заявки на обучение, аудитории.

## 2. Целевая архитектура ролей

### 2.1 Принцип
- **Разрешения** (что можно делать) задаются **в коде**: это каталог, потому что каждое разрешение проверяется конкретным кодом.
- **Роли** это **данные в БД**: админ создаёт роль, ставит галочки нужных разрешений, назначает роль пользователям.
- **Область данных** (свои или все) это часть разрешения, а не роли.

### 2.2 Таблицы (новая миграция)

```sql
CREATE TABLE roles (
  id            VARCHAR(191) PRIMARY KEY,
  code          VARCHAR(64)  NOT NULL UNIQUE,      -- 'ADMIN', 'METHODIST', ...
  name          VARCHAR(191) NOT NULL,             -- «Методист»
  description   TEXT NULL,
  is_system     BOOLEAN NOT NULL DEFAULT FALSE,    -- ADMIN нельзя удалить или ослабить
  base_profile  ENUM('STAFF','TEACHER','STUDENT') NOT NULL DEFAULT 'STAFF', -- какой кабинет, дашборд, меню
  priority      INT NOT NULL DEFAULT 0,            -- для защиты от повышения прав
  created_by    VARCHAR(191) NULL,
  created_at    DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at    DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  deleted_at    DATETIME(3) NULL
);

CREATE TABLE role_permissions (
  role_id     VARCHAR(191) NOT NULL,
  permission  VARCHAR(100) NOT NULL,               -- 'groups:create'
  PRIMARY KEY (role_id, permission),
  FOREIGN KEY (role_id) REFERENCES roles(id) ON DELETE CASCADE
);

ALTER TABLE users ADD COLUMN role_id VARCHAR(191) NULL,
                  ADD COLUMN permissions_version INT NOT NULL DEFAULT 0;
-- users.role (ENUM) оставляем на переходный период, затем удаляем
```

Одна роль на пользователя. Несколько ролей сразу не нужны: проще объяснять и проверять, а комбинация решается созданием новой роли. Таблицу `user_roles` можно добавить позже без поломки.

Персональные исключения («дать одному пользователю одно право без новой роли») сознательно не вводятся на первом этапе: они размывают аудит. Если понадобится, добавить `user_permission_overrides(user_id, permission, effect ALLOW|DENY)`.

### 2.3 Миграция существующих ролей
Сид создаёт 4 системные роли из текущего `ROLE_PERMISSIONS` 1:1 (`ADMIN`, `MANAGER`, `TEACHER`, `STUDENT`) и проставляет `users.role_id`. Поведение для пользователей не меняется. MANAGER, TEACHER и STUDENT после этого становятся редактируемыми (`is_system=false`); ADMIN остаётся системной ролью со всеми правами всегда (включая новые, добавленные в код позже).

### 2.4 Проверка на сервере
- `getPermissionContext(event)` загружает `role_id` → набор прав из кэша в памяти (Map roleId → Set). Кэш сбрасывается при любом изменении роли (в одном процессе PM2 сразу, в кластере через `roles.updated_at`/версию, проверяемую раз в N секунд).
- JWT хранит `userId` и `roleId`; права в токен **не кладём**, чтобы изменение роли действовало сразу, а не после истечения токена.
- Одна функция `requirePermission(event, perm)` / `requireAnyPermission`. Все прямые сравнения `role === 'ADMIN'` заменяются на проверку прав.
- `ROLE_PROTECTED_ROUTES` и мёртвый `API_PERMISSIONS` удаляются. Middleware отвечает только за аутентификацию (кто ты), эндпоинт за авторизацию (что тебе можно).
- **Страховка от забытых проверок:** каждый эндпоинт объявляет права через обёртку
  ```ts
  export default defineProtectedHandler({ permission: Permission.GROUPS_CREATE, audit: {...} }, async (event, ctx) => {...})
  ```
  или явно `defineProtectedHandler({ public: true }, ...)`. Плюс тест/скрипт CI, который проходит по `server/api/**` и падает, если файл не использует ни обёртку, ни `requirePermission`. Это то, что не позволит повторить ситуацию из раздела 0.

### 2.5 Область данных (scope)
Вместо `if (role === TEACHER)`:
- `groups:view_all` → все группы; `groups:view_own` → группы, где пользователь связан как инструктор (через `instructors.user_id`); то же для студентов, расписания, посещаемости, оценок, сертификатов, аттестации.
- `canAccessGroup(ctx, groupId)`: если есть `*_view_all` → да; иначе если есть `*_view_own` и привязанный `instructorId`/`studentId` → проверка связи.
- `instructorId`/`studentId` подгружаются для **любой** роли, у которой есть привязка, а не только для TEACHER/STUDENT.

### 2.6 Защита от повышения прав (anti-escalation)
- Управлять ролями может только тот, у кого `roles:manage`.
- Нельзя выдать роли право, которого нет у тебя самого (кроме ADMIN).
- Нельзя назначить пользователю роль, у которой есть права, которых нет у тебя.
- Нельзя изменить собственную роль и роль, к которой принадлежишь сам.
- Нельзя удалить или ослабить системную роль ADMIN; нельзя оставить систему без единого активного ADMIN.
- Удаление роли, на которой есть пользователи, запрещено: сначала переназначить.
- Права с пометкой «опасное» (удаление, управление ролями, настройки системы, просмотр аудита) в UI подсвечиваются красным и требуют подтверждения.

### 2.7 Клиент
- `GET /api/auth/me` возвращает `{ user, role: {id, code, name, baseProfile}, permissions: string[] }`.
- `usePermissions()` берёт права из этого ответа, а не из `ROLE_PERMISSIONS`. Код `app/types/permissions.ts` оставляет только enum и каталог (метаданные для UI).
- Каталог прав переезжает в `shared/permissions.ts` (папка `shared/` уже есть), одна копия на клиент и сервер.
- `PAGE_PERMISSIONS`, меню сайдбара, кнопки: только через `hasPermission`. Проверки `user.role === 'ADMIN'` на клиенте (9 файлов) заменить.
- `base_profile` решает только, какой кабинет показать (дашборд сотрудника, преподавателя или слушателя), но **не** права.

### 2.8 UI управления ролями
Новая страница `/admin/roles` (право `roles:view`, правка `roles:manage`):
- Список ролей: название, число пользователей, системная или нет, дата изменения.
- Редактор роли: название, описание, профиль кабинета; матрица прав по модулям. Строка = модуль, колонки = действия (Просмотр своих / Просмотр всех / Создание / Изменение / Удаление / Особые). Галочка «весь модуль». Поиск по правам. Подсказки, что даёт каждое право.
- Автоматические зависимости: при выборе `groups:update` автоматически ставится `groups:view_own` или `groups:view_all` (у каждого права есть `requires`).
- «Создать на основе» (клонирование роли).
- «Сравнить с ролью»: diff двух ролей.
- «Просмотреть как»: список страниц и действий, доступных роли (без входа под пользователем).
- Вкладка «Пользователи» роли и массовое переназначение.
- На странице пользователей вкладки по ролям заменяются фильтром по роли, а выбор роли берётся из таблицы `roles`.

## 4. Система аудита (журнал действий)

### 4.1 Что должно отвечать на вопросы
**Кто** (пользователь, его роль **на момент действия**, IP, устройство, «от чьего имени»), **когда** (миллисекунды, UTC), **что** (действие человеческим языком), **над чем** (тип, id, название, родитель: книга → группа), **какие изменения** (поле: было → стало), **результат** (успех, отказ в доступе, ошибка), **откуда** (веб, Telegram, интеграция, фоновая задача).

### 4.2 Новая таблица (рядом со старой; старая остаётся только для чтения)

```sql
CREATE TABLE audit_events (
  id              BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  occurred_at     DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  request_id      CHAR(36) NULL,               -- связывает все записи одного запроса
  actor_user_id   VARCHAR(191) NULL,           -- NULL = система / аноним
  actor_name      VARCHAR(191) NULL,           -- снимок, чтобы запись была читаемой после удаления пользователя
  actor_role_id   VARCHAR(191) NULL,
  actor_role_name VARCHAR(191) NULL,           -- снимок роли на момент действия
  source          VARCHAR(20) NOT NULL,        -- web | telegram | integration | system | cli
  action          VARCHAR(64) NOT NULL,        -- 'group.student_added', 'role.permissions_changed'
  category        VARCHAR(32) NOT NULL,        -- auth | access | data | security | system
  permission      VARCHAR(100) NULL,           -- каким правом действие разрешено
  entity_type     VARCHAR(64) NULL,            -- VARCHAR вместо ENUM: больше не теряем записи
  entity_id       VARCHAR(191) NULL,
  entity_label    VARCHAR(255) NULL,
  parent_type     VARCHAR(64) NULL,
  parent_id       VARCHAR(191) NULL,
  outcome         VARCHAR(16) NOT NULL,        -- success | denied | failed
  summary         VARCHAR(500) NOT NULL,       -- «Добавил слушателя Иванов И. в группу ПБ-12»
  changes         JSON NULL,                   -- [{field,label,before,after}]
  metadata        JSON NULL,                   -- количество, фильтры экспорта, причина отказа
  ip_address      VARCHAR(45) NULL,
  user_agent      VARCHAR(500) NULL,
  http_method     VARCHAR(10) NULL,
  http_path       VARCHAR(500) NULL,
  prev_hash       CHAR(64) NULL,               -- цепочка хэшей: подделка или удаление записи видны
  hash            CHAR(64) NULL,
  INDEX (occurred_at), INDEX (actor_user_id, occurred_at),
  INDEX (entity_type, entity_id, occurred_at), INDEX (action), INDEX (request_id)
);
```

### 4.3 Как писать
- Новый `server/utils/audit.ts`:
  ```ts
  await audit(event, {
    action: 'group.update',
    entity: { type: 'GROUP', id, label: group.code },
    before: oldGroup, after: newGroup,      // diff считается автоматически
    fields: GROUP_AUDIT_FIELDS,             // какие поля и с какими подписями сравнивать
  })
  ```
- `diff(before, after, fields)` пишет только изменённые поля с русскими подписями; пароли, токены, хэши, ключи AI маскируются (`***`) по общему списку.
- **Массовые действия** (импорт 300 студентов, массовая выдача доступа к книге, массовое удаление занятий) пишутся одной записью с `metadata.count` и списком id (до N штук, остальное «и ещё 280»), плюс при желании по записи на каждый объект с общим `request_id`.
- **Автоматика в обёртке `defineProtectedHandler`:** каждый мутирующий запрос (POST/PUT/PATCH/DELETE) без явного вызова `audit()` получает запись низкого уровня «вызван эндпоинт» с результатом. Так ни одно изменение не останется без следа, даже если разработчик забыл.
- **Отказы:** `requirePermission` при 403 пишет `outcome=denied` с недостающим правом. Неудачные входы, блокировки, сбросы паролей пишутся всегда (`category=security`).
- **Чтение чувствительного:** скачивание сертификата, просмотр ответов теста с правильными ответами, экспорт журнала, просмотр аудита: записываются `category=access`. Обычные просмотры списков не пишем (шум).
- Запись в аудит не должна ломать основной запрос, но ошибки записи не проглатываются молча: счётчик и предупреждение в лог сервера, а для `category=security` попытка повтора.
- Записи из фоновых задач и Telegram-бота: `source=system`/`telegram`, `actor_user_id` по привязке Telegram.

### 4.4 Что обязательно логировать (по модулям)
- **Роли и права:** создание, переименование, удаление роли; полный diff прав (добавлено: …, убрано: …); назначение роли пользователю (было → стало).
- **Пользователи:** создание, правка полей, блокировка, сброс пароля, удаление, входы (успешные и неудачные), выход, обновление токена с нового IP.
- **Программы, дисциплины, группы, расписание, посещаемость, оценки:** все изменения с diff (особенно оценки и посещаемость: кто поставил, кто исправил, было → стало).
- **Сертификаты:** выдача, ручная выдача, отзыв, удаление, перегенерация, правка шаблона.
- **Тесты:** создание и правка вопросов, назначение, завершение сессии, нарушения прокторинга, ручная правка результата.
- **Аттестация** (сейчас 0 логов): решения комиссии, состав комиссии, документы.
- **Библиотека:** загрузка, удаление, выдача и отзыв доступа, экспорт.
- **Файлы и папки:** загрузка, перемещение, удаление, установка или снятие пароля.
- **Система:** изменение настроек (diff, с маскировкой секретов), AI-настройки, вебхуки Telegram, миграции, перезапуск.

### 4.5 Интерфейс журнала
Переработать `/activity-logs`:
- Лента событий человеческим языком: «Иван Петров (Методист) изменил группу ПБ-12: дата окончания 01.12 → 15.12; аудитория 101 → 204».
- Фильтры: пользователь, роль, модуль, действие, объект, результат (успех / отказ / ошибка), период, IP, источник.
- **История объекта:** на карточке группы, студента, программы, книги вкладка «История изменений».
- **История пользователя:** на карточке пользователя вкладка «Действия».
- Раскрытие записи: таблица полей было/стало, request id, все записи этого же запроса.
- Экспорт в Excel/CSV (сам экспорт тоже пишется в аудит).
- Отдельная вкладка «Безопасность»: отказы в доступе, неудачные входы, изменения ролей.
- Проверка целостности цепочки хэшей (кнопка у админа).

### 4.6 Хранение
- Записи не удаляются через приложение. Хранение настраивается (по умолчанию 3 года); старые переносятся в архивную таблицу или файл, а не удаляются.
- Право `audit:view` не даёт права удалять.
- Старая таблица `activity_logs` отображается в той же ленте как «устаревшие записи» до окончания срока хранения.

## 8. Реализовано (2026-11-09), не закоммичено

**Гибкие роли (этапы 1–2, 5–6 плана).**
- Миграция `054_roles_and_audit`: `roles`, `role_permissions`, `users.role_id`; 4 базовые роли перенесены из `ROLE_PERMISSIONS` 1:1. С этого момента **источник прав — БД**, а `ROLE_PERMISSIONS` в коде служит только начальными значениями и запасным вариантом до миграции.
- `server/utils/roleRegistry.ts`: роль и права берутся из БД на каждом запросе (кэш 15 с), а не из JWT. Смена роли действует сразу, удалённый пользователь получает 401, подделанная роль в токене игнорируется.
- `users.role` теперь «профиль кабинета» (какой дашборд и меню): у кастомной роли это её `base_profile`.
- Все проверки в API переведены с названий ролей на права: группы, расписание, посещаемость, пользователи, тестовый банк, файлы, курсы, шаблоны, отчёты.
- Область данных («свои / все») определяется правами (`*_view_all` / `*_view_own`) и привязкой к инструктору или слушателю, а не названием роли.
- Защита от повышения прав: нельзя выдать роли или пользователю права сверх своих; нельзя менять свою роль и роль, в которой состоишь; системная роль ADMIN неизменна; нельзя оставить систему без администратора; роль с пользователями не удаляется.
- Новые права: `roles:view`, `roles:manage`, `groups:edit_locked`, `ai_chat:use`. Менеджеру выданы `users:create/update/delete` (как фактически было на сервере) и `schedule:delete`.
- Интерфейс: `/admin/roles` — матрица прав по модулям, зависимости, опасные права, «на основе», поиск. В карточке пользователя — назначение роли.

**Журнал аудита (этап 3, 7 плана).**
- Таблица `audit_events`, утилита `server/utils/audit.ts`: кто (с ролью на момент действия), что, над чем, поле «было → стало», результат, IP (с учётом доверенного прокси), устройство, источник, `request_id`, HTTP-статус. Секреты маскируются.
- Плагин `server/plugins/auditRequests.ts`: каждый изменяющий запрос и каждый отказ в доступе попадают в журнал автоматически.
- Все 120 существующих вызовов `logActivity` пишутся и в новый журнал. Разница «было → стало» добавлена в: пользователи, слушатели, группы, программы, расписание, инструкторы, организации, оценки, роли, назначение ролей.
- Неудачные входы журналируются; из ответа `/api/auth/login` убраны отладочные шаги, по которым можно было перебирать email.
- Интерфейс: `/admin/audit` — лента с фильтрами, раскрытием изменений, «все действия пользователя», «история объекта», «весь запрос», выгрузка CSV.

**Прочее:** `TRUST_PROXY_HOPS` (по умолчанию 1) — IP берётся из правой части `X-Forwarded-For`, подмена заголовка больше не обходит лимиты.

**Проверено вживую** (dev-сервер, локальная БД): прежние матрицы доступа без регрессий; сценарий гибких ролей — 31 из 32 проверок с первого прогона, последний провал был ошибкой фильтра журнала и исправлен; запись «было → стало» на реальном изменении с откатом.
